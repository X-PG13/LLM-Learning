## 本篇要回答的问题

1. 循环的每一步，模型采样的是什么？工具在哪一段运行？
2. 观察写回之后，下一步的条件多了哪一段？同一条抄写策略为什么会改口？
3. 单轮解码、检索之后只生成一次、工具循环，各在什么前提下使用？
4. 订单 1042 的两步轨迹里，每一步的状态是什么？选错工具、参数不合法、看见城市仍去查另一座城市，各留下什么观察？
5. 每步选对的概率是 2/3 时，两步都选对的概率是多少？1042 + 8 再加一步，延迟和失败概率各增加多少？

## 循环仍是下一步预测

状态是一串已经写下来的消息。因果语言模型给出的仍是

```text
p(下一段 token | 当前状态)
```

智能体把这一段 token 当成一个动作。动作可以是一次工具调用，也可以是结束：`finish(答案)`。一条动作是有限的 token 序列，它的概率是这些 token 的条件概率之积。乘法公式在 [Token 与下一个词](01-Token与下一个词.md)。本篇把整条动作收成一个候选，手算只在几个候选之间归一化，不再展开词表。

模型写完这条序列就停。运行时做三件事：解析工具名和参数，用谓词检查参数，通过之后才调用工具。工具的返回值由运行时追加成新的消息。模型的这一次前向不运行 `lookup_order`，也不运行 `lookup_weather`。

`finish` 没有工具可调。运行时不再追加工具消息，循环停止。

函数调用（function calling）把动作收成结构化的名字和参数，采样时可以只留下符合模式的序列。模式改变的是哪些 token 序列还能被采样。执行仍然在这次前向之外。ReAct 把推理文字和动作都写成普通文本：推理文字只是模型自己的 token，不触发外部系统；动作由环境执行，观察再写回上下文。两种写法的分工相同。字段名、停止原因和实验结果以论文和官方文档为准，不在本篇改写。

只生成推理文字、不调用工具，状态里新增的全是模型自己的 token。Wei 等的 chain-of-thought 属于这一类，材料在 [阅读清单](../08-研究习惯/阅读清单.md#wei-cot-2022)。工具循环多出来的是模型没有采样的那段观察。

示范轨迹上的监督仍是动作 token 的交叉熵，哪些位置进入分母见 [对齐](04-对齐.md)。本篇不算那一次平均。两条轨迹谁更好，也是那一篇的偏好对。

## 状态怎样接上观察

记 `s` 为当前消息列表。一步是

```text
动作 a ~ p(· | s)
若 a 是 finish：停止
否则：观察 o = 运行时(a)，s ← s 接上 a 和 o
```

下一步采样的条件是接上之后的 `s`。`o` 不在原来的 `s` 里，模型就读不到 `o` 里的字符串。把 `o` 丢掉再采样，条件回到「只有动作、没有观察」。

本篇的订单表只有两行，天气表只有三行。表以外的返回值都写在下面，手算不要再假设别的城市。

| 工具 | 通过谓词之后的返回 |
| --- | --- |
| `lookup_order(order_id)` | 1042 → 杭州，1001 → 北京；范围内的其他整数 → 无此订单 |
| `lookup_weather(city)` | 杭州 → 雨，北京 → 晴，上海 → 阴 |
| `add(left, right)` | 两个整数之和 |
| `order_weather(order_id)` | 先做订单查询；得到城市之后再查天气，只把天气写回 |

`lookup_order` 的谓词是：参数的类型是整数，并且 `1000 ≤ order_id ≤ 9999`。`"1042"` 这种字符串在类型这一步就停。谓词失败时，订单表不被读取，观察是「参数不合法」。`999` 和 `10000` 同样不读表。`1000` 和 `9999` 通过谓词，表里没有这两号，观察是「无此订单」。

天气的谓词是：城市属于 {杭州, 北京, 上海}。`add` 的两个参数都要是整数。`order_weather` 把上面的订单谓词和天气表接在工具内部，模型只看见最后一条观察。

温度 0 时，本篇用一条抄写策略读状态。它是确定性的，用来把消息列表走完：

- 最后一条观察是「参数不合法」或「无此订单」：`finish(无法回答)`。
- 已经有天气观察：雨写成 `finish(下雨)`，晴或阴写成 `finish(不下雨)`。
- 只有城市、还没有天气：`lookup_weather(该城市)`。
- 还没有任何工具观察：`lookup_order(题目里的订单号)`。

题目若是 `1042 + 8`，两个整数都在用户消息里。抄写策略不查订单，直接 `finish(1050)`。

温度 1 的概率在后面单独给。抄写策略走的是那组概率里质量最大的动作。

## 三种用法

| 问题里已经有什么 | 这一次怎么做 |
| --- | --- |
| `1042 + 8` 的两个整数都在用户消息里 | 单轮 `finish(1050)`。`1042 + 8 = 1050` |
| 退货天数在外部文档里，用户消息没有写出天数 | 检索器先把文本放进同一次生成的条件。模型不根据第一段观察再决定下一次查询。切块、BM25 和召回率在 [检索增强生成](06-检索增强生成.md) |
| 用户消息里已经写着「七天」 | 单轮解码。检索不再提供这道题缺的字符串 |
| 订单 1042 的城市和该城市的天气都要读，两个工具是分开的 | 工具循环。第二次查询的城市来自第一次观察 |
| 同上，但运行时提供 `order_weather` | 一次工具调用。1042 的观察直接是「雨」 |

检索增强和工具循环都可以读到模型参数里没有的字符串。差别在谁决定下一次读什么。检索器在生成前（或同一次生成所用的那批块上）选定文本。工具循环里，下一次工具名和参数来自模型对**已经包含上一次观察**的状态的预测。

`order_weather(1042)` 内部仍要读两张表。对模型的状态来说，写回的是一条观察，循环只多一次工具。步数是工具界面的长度，不是问题句子里自带的步数。

## 两步查找

问题：订单 1042 的收货城市今天下雨吗？温度取 0，走抄写策略。

第 0 步，模型读到的状态：

```text
[user] 订单 1042 的收货城市今天下雨吗？
```

动作是 `lookup_order(order_id=1042)`。1042 是整数，落在闭区间里，表里有这一行。运行时写回「杭州」。写回之后的状态：

```text
[user] 订单 1042 的收货城市今天下雨吗？
[assistant] lookup_order(order_id=1042)
[tool] 杭州
```

第 1 步的条件比第 0 步多了动作和「杭州」。抄写策略读到城市、还没有天气，动作是 `lookup_weather(city=杭州)`。运行时写回「雨」：

```text
[user] 订单 1042 的收货城市今天下雨吗？
[assistant] lookup_order(order_id=1042)
[tool] 杭州
[assistant] lookup_weather(city=杭州)
[tool] 雨
```

第 2 步的条件里有「雨」。动作是 `finish(下雨)`。运行时不再追加工具消息，循环停止。

「杭州」和「雨」都不是用户消息里的字。它们进入下一步，是因为运行时把观察接了上去。删掉「杭州」这一条，状态里没有城市，抄写策略回到 `lookup_order(1042)`，不会发出 `lookup_weather(杭州)`。

把订单号换成 1001，同一条策略读到的第一份观察是「北京」。第 1 步的动作变成 `lookup_weather(city=北京)`，观察是「晴」，然后 `finish(不下雨)`。策略没改，第二步的参数跟着观察改。

本篇把一条轨迹叫做**支持的**，要同时满足四条：

1. 状态里有 `lookup_order(正确订单号)`，观察等于该订单的城市。
2. 在这之后才有 `lookup_weather`，参数等于那次城市观察，观察等于该城市的天气。
3. `finish` 在天气观察之后。
4. 雨对应 `finish(下雨)`，晴或阴对应 `finish(不下雨)`。

**答案正确**只看 `finish` 的字符串是否等于该订单的真实天气：1042 的真实天气是雨，字符串应是「下雨」；1001 是晴，字符串应是「不下雨」。两个比例的分母可以是同一批订单，分子看的东西不同。一个分数在回答哪一个问题，见 [评估](05-评估.md)。下面的计数只覆盖本篇这几条轨迹。

上面 1042 的三步四条都满足，答案也正确。1001 的反事实同样支持，答案是「不下雨」。

## 失败时状态停在哪里

### 第一步就选了天气

动作 `lookup_weather(city=北京)` 通过天气谓词。运行时写回「晴」。状态里没有订单观察。按这份观察结束，得到 `finish(不下雨)`。

| 订单 | 真实天气 | 这条轨迹的 finish | 答案正确 | 轨迹支持 |
| --- | --- | --- | --- | --- |
| 1042 | 雨 | 不下雨 | 否 | 否 |
| 1001 | 晴 | 不下雨 | 是 | 否 |

两张订单上，答案正确率是 1/2，轨迹支持率是 0。1001 对上，是因为猜中的城市恰好是这张订单的城市，订单表没有被读。换一批订单，这个 1/2 可以变。

### 参数不合法

`lookup_order(order_id=104)`：104 小于 1000。运行时不读订单表，写回「参数不合法」。抄写策略见到这条错误，下一步是 `finish(无法回答)`。

八个调用分三类：

| 调用 | 观察 | 订单表 |
| --- | --- | --- |
| `1042` | 杭州 | 读了 |
| `1001` | 北京 | 读了 |
| `1008` | 无此订单 | 读了 |
| `1000` | 无此订单 | 读了 |
| `9999` | 无此订单 | 读了 |
| `999` | 参数不合法 | 不读 |
| `10000` | 参数不合法 | 不读 |
| `"1042"` | 参数不合法 | 不读 |

读到城市的有 2 个，读了表但没有这张订单的有 3 个，谓词拒绝的有 3 个。`1000` 和 `9999` 在闭区间里。字符串 `"1042"` 和整数 1042 不是同一个参数。

### 观察已经在状态里，动作仍用另一座城市

第 0 步已经写回「杭州」。第 1 步若仍发出 `lookup_weather(city=北京)`，运行时写回「晴」，因为北京的天气就是晴。按这份观察结束，是 `finish(不下雨)`。

```text
[user] 订单 1042 的收货城市今天下雨吗？
[assistant] lookup_order(order_id=1042)
[tool] 杭州
[assistant] lookup_weather(city=北京)
[tool] 晴
[assistant] finish(不下雨)
```

1042 的真实答案是「下雨」。答案不正确。天气调用的参数是北京，不是已经写回的杭州，轨迹也不支持。「杭州」在状态里，下一步的动作没有用它。

先发出 `lookup_weather(杭州)`、之后才 `lookup_order(1042)`，天气调用发生时状态里还没有这张订单的城市。即便两个字符串后来对上，轨迹支持仍为假。支持看的是写回的顺序，不只是最终消息里出现过哪些字。

## 一步的概率怎样乘成轨迹

温度 1。每一步有三个候选动作，logits 是 `(ln 4, 0, 0)`。

```text
exp(ln 4) = 4
exp(0) = 1
exp(0) = 1
总和 6
概率 = 4/6, 1/6, 1/6 = 2/3, 1/6, 1/6
```

质量 4 的那条，是抄写策略在这一状态下会选的动作。另外两条各占 1/6，本篇把它们具体写成：

| 这一步的条件 | 质量 4 | 质量 1 | 质量 1 |
| --- | --- | --- | --- |
| 还没有工具观察 | `lookup_order(题目订单号)` | `lookup_weather(北京)` | `finish(下雨)` |
| 城市观察是杭州，还没有天气 | `lookup_weather(杭州)` | `lookup_weather(北京)` | `finish(下雨)` |
| 用户消息是 `1042 + 8` | `finish(1050)` | `finish(1042)` | `add(1042, 8)` |

这组 2/3 是为了把连乘留在分数里，不是某个已训练模型在这道题上测出来的准确率。温度 0 取唯一的最大项。两步查找会走上一节写全的那条成功轨迹；加法会走单轮 `finish(1050)`。下面的 4/9 是温度 1 抽样、前后两步都抽到质量 4 的概率。

第二步的 2/3 带条件。查天气时，条件是第一步已经写回正确城市；做加法时，条件是 `add` 已经写回 1050。第一步若没写回那条观察，轨迹已经失败，不再乘第二步的 2/3。

```text
P(两步都选对) = (2/3) × (2/3) = 4/9
P(第一步失败) = 1/3
P(第一步选对且第二步失败) = (2/3) × (1/3) = 2/9
P(失败) = 1/3 + 2/9 = 5/9
```

`1 − 5/9 = 4/9`，和连乘一致。

单轮只有一个决定，失败概率是 1/3。再增加一个同样是 2/3 的决定，失败概率变成 5/9，多出 `5/9 − 1/3 = 2/9`。成功概率从 2/3 变成 4/9，少掉的也是 2/9。

`1042 + 8` 在温度 0 下走上面那一行，是单轮 `finish(1050)`。`add` 在这一行里只占 1/6。若另定一条两步策略，把第一步的质量 4 改放到 `add(1042, 8)` 上，写回 1050 之后再把质量 4 放在 `finish(1050)` 上，两步都抽中的概率是 4/9，比单轮的 2/3 少 2/9。观察 1050 可以从用户消息里的两个整数算出来，这一步工具没有提供新的外部事实。

先把 2/3 收成四位小数 0.6667，再平方，得到 `0.44448889`，收到四位是 0.4445。`4/9 = 0.4444…`，收到四位是 0.4444。连乘用 4/9，不要用已经收位的 0.6667 回乘。

## 多一步的延迟

一次模型调用生成 `N` 个新 token 的时间，用推理优化里的式子：

```text
TTFT + (N − 1) × TPOT
```

本篇取 `TPOT = 10` 毫秒。每个工具再加 20 毫秒，几个工具都用这一个数，差别只来自步数。已经写回的工具观察有 `k` 条时，`TTFT = 40 + 30k` 毫秒。这 30 毫秒是这条轨迹上填的增量，用来把式子算完；prefill 和 KV cache 怎样随 token 增长，在 [推理优化](../07-系统工程/02-推理优化.md)，这里不重算字节。

工具动作按 `N = 5` 计，`finish` 按 `N = 3` 计。

| 轨迹 | 调用 | 毫秒 |
| --- | --- | --- |
| 单轮 `finish(1050)` | `k = 0`，`N = 3` | `40 + 2 × 10 = 60` |
| 一次工具再结束 | `k = 0` 的工具动作，工具 20，`k = 1` 的 `finish` | `80 + 20 + 90 = 190` |
| 两次工具再结束 | 再加 `k = 1` 的第二次工具动作、第二个工具 20，并且 `finish` 的 `k = 2` | `80 + 20 + 110 + 20 + 120 = 350` |

一次工具的 80 是 `40 + 4 × 10`，90 是 `70 + 2 × 10`。两次工具比一次工具多 `350 − 190 = 160` 毫秒。这 160 是三笔：第二次工具动作 `70 + 4 × 10 = 110`，第二个工具 20，以及 `finish` 的 TTFT 从 70 增到 100 的那 30。`110 + 20 + 30 = 160`。

`1042 + 8` 走单轮是 60 毫秒。先调用 `add` 再结束，和「一次工具再结束」同一张账，是 190 毫秒。多出来的 130 毫秒没有换成外部系统里的新事实。

订单天气若改用 `order_weather`，模型侧也是「一次工具再结束」，190 毫秒，观察是「雨」。拆成两个工具是 350 毫秒。`order_weather(1042)` 返回雨，`order_weather(1001)` 返回晴，`order_weather(1008)` 返回「无此订单」，`order_weather(104)` 返回「参数不合法」。

把单轮写成 `TTFT + N × TPOT`，得到 `40 + 3 × 10 = 70`。第一个 token 的时间已经在 TTFT 里，又被乘进了 TPOT，多了 10 毫秒。推理优化那篇用另一组毫秒算过同一种重复计数。

## 参考代码

订单表和天气表就是正文那两张。`copy_weather` 是订单问题在温度 0 下的抄写策略。`trace_supported` 要求天气调用发生在城市观察写回之后。

```python
from fractions import Fraction


ORDERS = {1042: "杭州", 1001: "北京"}
WEATHER = {"杭州": "雨", "北京": "晴", "上海": "阴"}


def lookup_order(order_id):
    if type(order_id) is not int or not 1000 <= order_id <= 9999:
        return "参数不合法"
    return ORDERS.get(order_id, "无此订单")


def lookup_weather(city):
    if city not in WEATHER:
        return "参数不合法"
    return WEATHER[city]


def order_weather(order_id):
    city = lookup_order(order_id)
    if city in ("参数不合法", "无此订单"):
        return city
    return WEATHER[city]


def add(left, right):
    if type(left) is not int or type(right) is not int:
        return "参数不合法"
    return left + right


def copy_weather(order_id, observations):
    if observations and observations[-1] in ("参数不合法", "无此订单"):
        return ("finish", "无法回答")
    city = None
    weather = None
    for obs in observations:
        if obs in ORDERS.values():
            city = obs
        if obs in WEATHER.values():
            weather = obs
    if weather is not None:
        answer = "下雨" if weather == "雨" else "不下雨"
        return ("finish", answer)
    if city is not None:
        return ("lookup_weather", city)
    return ("lookup_order", order_id)


def trace_supported(order_id, events):
    city = None
    weather = None
    for kind, arg, obs in events:
        if kind == "lookup_order" and arg == order_id and obs == ORDERS.get(order_id):
            city = obs
        elif kind == "lookup_weather" and city is not None and arg == city and obs == WEATHER.get(arg):
            weather = obs
        elif kind == "finish":
            if city is None or weather is None:
                return False
            expected = "下雨" if weather == "雨" else "不下雨"
            return arg == expected
    return False


def action_probs():
    return tuple(Fraction(mass, 6) for mass in (4, 1, 1))


def model_ms(ttft, n_tokens, tpot=10):
    return ttft + (n_tokens - 1) * tpot


def ttft(n_observations):
    return 40 + 30 * n_observations
```

## 容易算错的地方

- 模型的前向执行了工具。工具在运行时里运行；写回状态的是观察消息。
- 删掉「杭州」之后，下一步仍是 `lookup_weather(杭州)`。没有这条观察时，抄写策略回到 `lookup_order(1042)`。
- 1001 的第二步仍查杭州。同一条抄写策略读到的城市是北京。
- 字符串 `"1042"` 被当成整数。它的观察是「参数不合法」，订单表不读。
- `1000` 和 `9999` 被放在区间外面。闭区间内、表里没有的订单，观察是「无此订单」。
- 两张订单上都先查北京的天气，答案正确率写成 1。1001 的「不下雨」碰巧对上，1042 不对，比例是 1/2；两条轨迹的支持都是 0。
- 状态里已经有杭州，仍把 `lookup_weather(北京)` 的观察当成杭州的天气。写回的是「晴」，`finish` 是「不下雨」。
- 先猜对杭州的天气、再查订单，算成支持。天气调用时城市观察还没写回，支持为假。
- 两步成功概率写成 2/3。温度 1 下两步都抽到质量 4，才是 4/9；温度 0 走的是抄写策略那条成功轨迹。
- 用 0.6667 回乘。四位结果是 0.4445，`4/9` 收到四位是 0.4444。
- `1042 + 8` 仍去调工具。两个整数已经在用户消息里，单轮是 `finish(1050)`，60 毫秒。先 `add` 再结束是 190 毫秒，成功概率从 2/3 变成 4/9。
- 端到端时间写成 `TTFT + N × TPOT`。单轮从 60 毫秒变成 70 毫秒。
- 两次工具和一次工具的差只算了第二个工具的 20 毫秒。模型侧还多 110 毫秒，结束那一步的 TTFT 还多 30 毫秒，合计 160。

## 练习

### 练习 1：把两步状态写全

- 目标：下一步的参数等于上一次写回的城市。
- 限制：纸笔。用抄写策略，温度 0。
- 题面：订单 1042，写出三次模型调用各自读到的状态里有哪些观察，以及发出的动作。订单 1001 的第 1 步动作和最后的 `finish` 是什么？删掉 1042 轨迹里的「杭州」之后，抄写策略的下一步是什么？
- 完成标准：1042 依次是 `lookup_order(1042)` → 杭州，`lookup_weather(杭州)` → 雨，`finish(下雨)`。1001 的第 1 步是 `lookup_weather(北京)`，观察「晴」，`finish(不下雨)`。删掉「杭州」之后回到 `lookup_order(1042)`。

<details>
<summary>参考解答</summary>

第 0 步的状态只有用户消息。1042 在表里，观察是杭州。第 1 步因此查杭州，观察是雨，第 2 步结束为「下雨」。1001 的第一份观察是北京，天气是晴，结束语是「不下雨」。没有城市观察时，策略的第四条是按题目里的订单号再查一次订单。

</details>

### 练习 2：八个订单参数

- 目标：谓词和订单表是前后两道门。
- 限制：纸笔。闭区间，字符串不等于整数。
- 题面：正文八个调用里，哪些返回城市，哪些是「无此订单」，哪些是「参数不合法」？各有几个？`order_weather(1042)` 和 `order_weather(104)` 各返回什么？
- 完成标准：城市 2 个（杭州、北京），「无此订单」3 个（1008、1000、9999），「参数不合法」3 个（999、10000、`"1042"`）。`order_weather` 返回「雨」和「参数不合法」。

<details>
<summary>参考解答</summary>

1042 和 1001 在表里。1000、1008、9999 通过谓词，不在表里。999 和 10000 在区间外，字符串在类型这一步失败，三都不读表。`order_weather` 把城市留在工具内部，1042 只把雨写出来；104 在订单谓词上已经失败。

</details>

### 练习 3：两步概率

- 目标：第二步的 2/3 带条件，连乘之前不收位。
- 限制：纸笔。分数约分。四位小数只在最后一问使用。
- 题面：三个候选的概率是多少？两步都选对、两步失败、只第一步失败、第一步对且第二步失败，各是多少？比单轮多出来的失败概率是多少？把 2/3 先收成 0.6667 再平方，四位小数是多少？它和 `4/9` 的四位小数差在哪一位？
- 完成标准：概率 `2/3`、`1/6`、`1/6`。两步成功 `4/9`，失败 `5/9`，只第一步失败 `1/3`，第一步对且第二步失败 `2/9`。多出来的失败是 `2/9`。四位回乘是 0.4445，`4/9` 是 0.4444。

<details>
<summary>参考解答</summary>

`4/6 = 2/3`。`(2/3)×(2/3) = 4/9`。`1/3 + 2/9 = 5/9`。`5/9 − 3/9 = 2/9`。`0.6667 × 0.6667 = 0.44448889`，收到四位进到 0.4445。未收位的 `4/9` 在第四位仍是 4。

</details>

### 练习 4：三档延迟

- 目标：步数同时进入模型调用和工具次数。
- 限制：纸笔。用 `TTFT + (N − 1) × TPOT`，`TPOT = 10`，`TTFT = 40 + 30k`。
- 题面：单轮、一次工具、两次工具各多少毫秒？两次比一次多出的 160 怎样分成三笔？单轮若写成 `TTFT + N × TPOT`，得到多少，多出来的 10 毫秒是什么？`1042 + 8` 先调用 `add` 再结束，是哪一档？
- 完成标准：60、190、350。三笔是 110、20、30。错误式子得到 70。先 `add` 再结束是 190。

<details>
<summary>参考解答</summary>

`k = 0`、`N = 3`：`40 + 20 = 60`。一次工具：`80 + 20 + 90 = 190`。两次工具再加 `110 + 20`，并且结束步的 TTFT 是 100 而不是 70，所以是 `190 − 90 + 110 + 20 + 120 = 350`。`40 + 30 = 70`，多乘的那一次是第一个 token。`add` 只写回一条观察，账和一次工具相同。

</details>

### 练习 5：这道题用哪一种

- 目标：下一次查询依赖不依赖还没写回的观察。
- 限制：纸笔。检索的切块和召回率不在本题重算。
- 题面：下列五句各用单轮、检索后一次生成，还是工具循环？`1042 + 8`；退货天数在文档库里、用户没写天数；用户消息已经写了「七天」；订单天气且两个工具分开；订单天气且只有 `order_weather`。最后一种对 1042 写回什么？
- 完成标准：单轮 `finish(1050)`；检索后一次生成；单轮；两步工具循环；一次工具，写回「雨」。

<details>
<summary>参考解答</summary>

加法的两个整数已经在条件里。退货天数要靠检索器放进同一次生成；用户已经写了「七天」时，这份字符串不靠检索提供。分开的两个工具里，天气参数来自订单观察。`order_weather` 把两次查找留在工具内部，模型只看见雨。

</details>

### 练习 6：三条失败轨迹

- 目标：答案字符串和轨迹支持可以一个对、一个错。
- 限制：纸笔。用正文的两张订单。
- 题面：两张订单都先 `lookup_weather(北京)` 再按观察结束。答案正确率、轨迹支持率各是多少？`lookup_order(104)` 的观察是什么，订单表读了吗？下一步抄写策略发出什么？1042 已经写回杭州，仍 `lookup_weather(北京)`，观察和 `finish` 是什么，答案正确吗，轨迹支持吗？
- 完成标准：正确率 `1/2`，支持率 0。观察是「参数不合法」，表不读，下一步 `finish(无法回答)`。忽略杭州时观察是「晴」，`finish(不下雨)`，答案不正确，轨迹不支持。

<details>
<summary>参考解答</summary>

北京的天气是晴，结束语是「不下雨」。这和 1001 的真实天气一致，和 1042 不一致；两条都没有订单观察，支持都是 0。104 在谓词上失败。杭州已经写回时仍查北京，写回的是北京的晴，不是杭州的雨。

</details>

## 本篇之外

采样时就把非法参数的概率压成 0，和本篇先写出动作再拒绝，用的是同一类谓词，位置不同。本篇算的是后一种：八个订单调用里有三个被拒绝。并行的多个工具调用、多模型分工、树搜索，不在本篇。模型写出程序、由解释器执行，分工和本篇相同；Gao 等的 PAL 是这条线上的论文，本篇不另做一道程序题。

Toolformer 用「这次调用有没有降低后面 token 的损失」决定训练文本里留下哪些调用。那是训练时的筛选。本篇的 4/9 是给定动作分布之后的抽样概率，不是那条损失。

奖励模型、偏好对和 DPO 的间隔在 [对齐](04-对齐.md)。检索的召回、切块和上下文预算在 [检索增强生成](06-检索增强生成.md)。KV cache 的字节、连续批处理和量化在 [推理优化](../07-系统工程/02-推理优化.md)。本篇的抄写策略、八个参数、4/9 和三档毫秒由 `check_agents` 复核。
